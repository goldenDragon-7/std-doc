the moat: add a visual by writing a module, never editing the core

3.1 §1Why it exists

architecture
A doc engine that documents a large, evolving system must grow new visuals without a whole-system release. The renderer splits into a stable CORE and a swappable LIBRARY of primitives, so a new component is one self-contained module against a frozen contract.
The CORE
Owns the doc-tree walk, node numbering, left-nav, anchors (data-cf-change / data-cf-anchor), CSS/asset dedup, freeze orchestration, the palette, and the security gate. It never knows what a 'swimlane' is.
  • go/internal/{core,registry,gate}/MEASUREDthe shipped engine: core (walk, page, palette, diagrams), registry (the dispatch table), gate (the freeze security gate) — conformance 8/8 byte-identical
The LIBRARY
36 first-party primitives — 30 template-driven (data → HTML by a declarative template in go/stddoc-lib/templates.json) plus 6 code-driven (sections, diagrams, statetrack, swimlane, tree, evidence). Each turns one typed block into HTML and nothing more.
  • go/internal/core/install.goMEASUREDbuildRegistry installs all 36: the 30 template-driven (auto-registered from templates.json) + 6 code-driven, each Register(type, renderFunc, css)
The moat
No other doc engine binds ONE named-entity palette across every component AND closes the agent-edits-back loop. Comment capture is commodity; this pairing is not.
🌿

3.1 §2How it was built — strangler-fig

migration
The renderer was not rewritten in place. Today's hand-ordered render_node was wrapped as primitives BYTE-IDENTICAL first (the golden-master gate), then the core was hollowed out behind the contract.
Decisions D1–D6
BUILD the renderer + palette (the moat); ADOPT only the diagram layer (D2 binary, Mermaid fallback). Clean-room a small registry (studied markdown-it-py, depend on none) — 85 LOC in the shipped Go. Port the token→CSS pattern (Style Dictionary's idea), stay dependency-free. Contract is language-agnostic, which is why the Go port re-implemented it without re-designing — conformance 8/8 byte-identical.
Phased P0–P6
P0 contract + probes → P1 strangler-wrap existing renderers → P2 blocks[]+lint → P3 palette + palette-bound primitives → P4 D2 diagrams → P5 security gate → P6 standalone bespoke pages.
  • docs/proposals/pluggable-renderer/PRD.mdCITEDthe by-descent PRD + WBS that drove the build
Make the renderer pluggable — add an idiom without touching the core.
One stable contract in; a self-contained primitive module out. The core never learns a new type.
